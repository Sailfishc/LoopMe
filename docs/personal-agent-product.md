# LoopMe Personal Agent：当前产品定义

更新：2026-11-05。依据：用户第二轮明确的产品边界。本文区分已确认方向与待定行为，不代表实现已完成。

## 已确认的产品定位

以 Remmo 的轻量桌面常驻、手机配对和跨端体验为主要参考，提供一个长期存在的 Personal Agent。体验方向参考 OpenAI Dots / Grok Bot，具体竞品行为仍需单独核查。

用户面对的是自己的 Agent、对话、主动消息与事项，不需要认识或管理 Codex thread。第一版不以跨会话工程管理工作台为中心，也不要求每个跟进事项都先变成用户确认的任务。

## 产品边界

- 桌面端承载 Personal Agent 的主要能力，包括调用 Codex、定时唤醒和生成主动消息。
- Agent Runtime 完全复用 Codex CLI 或 App Server，不另建模型执行循环。具体接入方式尚未最终确定。
- Relay 提供手机与桌面之间的连接转发，不保存用户数据，不做账号体系或用户管理。
- 手机与桌面通过配对建立关系；配对设备不等于注册用户。
- 手机端第一版必须支持推送与事项处理。
- Codex thread 属于内部执行细节，不能成为用户必须选择、切换或维护的产品对象。

Relay 不持久化用户内容，允许保存最小设备路由与推送 Token 等元数据，不建立用户账号。桌面承载自己的数据存储；不可将这一边界扩大宣传为整个产品不存储数据。

## 主动性与权限

- 通过定时任务唤醒 Agent，分析当前上下文并决定是否产生提醒、事项或授权范围内的行动。
- 跟进机制允许半黑盒：用户无需维护显式任务图，可设置 profile 和 memory。
- 本期主动权由用户设置与产品调优共同确定，具体默认值和动作分类待定。
- 第一版可以读写，采用用户授权的 auto 模式；允许哪类行为，以用户授权和 Codex 权限能力为准。
- auto 是用户描述的产品意图，尚未映射为某个确定的 Codex 配置值。实现前需核实审批策略、沙箱及工具权限的实际组合。
- 产品调优可以改变建议质量、唤醒策略和主动倾向，不能扩大用户授予的权限。

## 面向用户的体验提案

初次使用：桌面建立 Agent → 设置简要 profile 与初始 memory → 授予所需访问和读写权限 → 手机配对并授权通知。

日常使用：用户与同一个 Agent 对话；Agent 按计划醒来，参考记忆与可访问的信息，必要时做授权范围内的工作，再决定是否通知。

手机消息应能继续同一话题、查看事项和处理需要用户决定的动作；内部的 thread 创建、恢复和轮换由产品负责。

尚需定义事项的最小操作集合，例如继续交流、稍后提醒、完成、不再跟进，以及任务运行中的停止或审批。上述集合是提案，非全部已确认要求。

## 建议的职责分配

桌面：身份与偏好、长期记忆、定时任务、Codex 接入、权限状态、事项与消息状态、配对关系。

Relay：在线连接路由、载荷转发与推送投递；允许保存最小路由元数据，不保存对话、memory、事项内容或离线消息队列。

手机：配对、接收通知、查看与处理事项、对话和用户决策。是否保存本地缓存、缓存范围与清理方式待定。

采用端到端加密是推荐方案，密钥、设备撤销和重配规则尚未定稿。

## 无云端数据存储带来的具体行为

以下是方案需要满足的现实约束，不是额外产品扩展：

- 桌面休眠或离线时，无法依赖桌面继续推理、执行和响应手机请求。
- 不保存云端消息队列时，离线补发需要由桌面持有待发状态；手机离线后的状态同步以桌面为来源。
- 手机后台推送通过 APNs 等平台服务投递；Relay 可以保存最小设备路由元数据。通知只是提醒，不能作为事项状态的权威来源。
- “无用户管理”仍需要设备配对、授权与撤销，否则无法判定哪个手机有权控制桌面。

## 第三轮已确认的行为

用户接受上一轮全部四项推荐：

1. Mac 在线且可运行是主动工作和实时响应的前提；离线时手机仅显示本地已有内容和不可达状态。
2. Relay 可以保存最小设备标识和推送 Token 等路由元数据，不保存用户内容，不建立账号体系。
3. Agent 可以自动维护 memory，用户可以查看、纠正和删除；profile 以用户明确设置为准。
4. 产品提供默认唤醒计划，用户可以调整、暂停和设置安静时段；Agent 可以在没有有用变化时保持安静。

## 桌面通过 Relay 提供服务

可行。桌面是业务服务端和数据权威来源，Relay 提供被配对设备访问的传输通路。桌面主动建立出站连接，手机发出的加密请求经 Relay 到达桌面；桌面验证配对与权限，调用自己的业务模块、存储和 Codex，再把结果或事件流返回手机。

桌面无需开放公网入站端口，但出站网络仍需可达；企业代理、防火墙、网络断开等条件可能阻断连接。端到端加密需额外实现，WSS 本身只保护各段传输。

可以暴露的应用服务包括：对话输入与流式回复、profile/memory 查询与修改、事项查询与处理、计划设置、授权范围内的任务启动和停止、审批、受限的附件传输。具体端点与能力仍需实现，Relay 本身不会自动赋予这些能力。

手机访问桌面定义的业务 API，不直接访问数据库，也不直接获得原始 Codex App Server 或任意本地端口的访问权。桌面统一校验请求与维护状态；重试以请求标识去重，防止重复执行写操作。

用户提到桌面有自己的“Mamba”。该名称含义尚未确认，不擅自映射成模型、memory 或 runtime；无论它最终是哪类本地组件，都可在明确接口后由桌面服务调用，再通过 Relay 返回结果。

## Relay 能力与局限

- 可负责在线路由、连接保持、重连协助、短暂有界内存缓冲、传输流控、设备连接鉴别、速率限制和推送投递。
- 不保存业务内容时，不能在桌面离线后回答历史查询、执行 Agent、生成新摘要或提供云端恢复。内存缓冲不提供离线可靠队列，进程退出即丢失。
- 端到端加密时，Relay 不理解消息语义；业务权限、状态更新、记忆处理与通知内容生成在桌面完成。
- 不设账号不等于不认证。配对密钥证明设备身份；桌面维护最终授权与撤销状态，Relay 使用必要的路由访问凭据限制滥用。
- Relay 仍能看到连接时间、IP、载荷大小等传输元数据；最小化日志，避免把用户内容间接写入日志或错误追踪。
- 手机后台通知依赖操作系统推送，不能用常驻 WebSocket 假定后台在线。APNs 接受不等于送达或已读，静默推送尤其不保证唤醒。
- 无云端内容队列时，桌面保存待投递状态和恢复所需记录；手机也可保存未送达操作，但应明确显示未送达，重新连接后再次校验时效与授权。
- Relay 转发大文件和长流会占用带宽、连接和内存；需要限制载荷并处理慢客户端。不能将无内容存储等同于零服务成本。
- 桌面数据丢失后，Relay 无法恢复；备份能力不在当前已确认范围内。

建议的第一版通知是低敏的“你的 Agent 有新消息”，正文由手机连接桌面取得。丰富通知与加密载荷的本地解密可后续研究，不影响第一版基本链路。APNs 自身可能临时保存待投递通知，应区分“我们的 Relay 不存内容”与“整个推送链路不存任何数据”。
