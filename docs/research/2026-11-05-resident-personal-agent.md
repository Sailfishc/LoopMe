# LoopMe：基于 Codex 的常驻个人工作 Agent

日期：2026-11-05。状态：研究与待讨论提案，不是已批准的实现规格。

## 1. 当前方向（用户第二轮澄清后）

当前产品边界以 [Personal Agent 产品定义](../personal-agent-product.md) 为准。下文第 3–11 节保留第一轮探索供追溯，属于历史提案；与当前定义冲突的建议不再适用。

用户已明确：重点参考 Remmo；核心是个人 Agent；桌面承载主要能力；Relay 不保存用户数据、不做账号和用户管理；手机与桌面配对；Runtime 完全基于 Codex CLI / App Server，用户不感知 thread；通过定时任务实现主动推送；跟进事项可以半黑盒，用户可设置 profile 和 memory；本期主动权通过用户设置与产品调优共同确定；第一版支持经用户授权的读写 auto 模式，权限基于 Codex；手机推送与事项能力属于第一版。

这取代此前“先做多会话工程观察器”“只读主动分析”“候选事项逐项确认”的默认建议。Dots / Grok Bot 是体验方向参照，尚不构成其具体实现方式的技术证据。

## 2. 公开资料核查与纠偏

以下为本次读取的公开文档行为，不代表本机或端到端实验已通过。

### Codex

- App Server 提供 thread/start、thread/read、thread/list、thread/resume、turn/start、turn/steer、turn/interrupt，以及结构化事件与审批交互。[S1]
- thread/loaded/list 返回当前服务内存中加载的线程，不能当成整个 Mac 上正在工作的 Codex 清单。[S1]
- thread/resume 恢复持久化线程，不足以证明可无损接管另一个独立运行的 CLI 或保证多写入者协调。[S1]
- 支持 stdio、Unix socket；文档将普通 WebSocket transport 标注为 experimental and unsupported。优先验证本地连接，再经自己的受控服务提供跨设备访问。[S1]
- thread/goal/set 的 tokenBudget、thread/tokenUsage/updated、account/rateLimits/read 可提供预算和资源信号，但没有因此获得整个产品的每日总预算、通知预算或严格美元费用上限。[S1]
- Hooks 覆盖 SessionStart、SessionEnd、Stop、Interrupt、工具与模型事件；支持 async。非托管 Hook 需经过审核后运行，不能承诺完全零配置。[S2]
- 官方区分本地/开源 App Server 集成与商业/托管服务，商业认证需要按 Sign in with ChatGPT 的适用资格与路径单独核查。[S1][S3]
- 长期运行还需考虑认证续期。Sign in with ChatGPT 的 App Server 接入文档描述更新访问令牌、重启服务并恢复线程的流程；具体认证模式不可混用。[S3]

结论：Codex 可承担执行与分析，但“观察全部现有会话”“共享同一活跃会话”“跨设备持续可用”需要分别验证。

### Happy

Happy 文档确认持久会话、跨设备连接、提醒，以及 Chief of Staff。后者主要负责初始化、模型配置、设备连接、部署与创建 Bot；这并不等于已经证明其能持续识别用户工作中的高价值下一步。[S4][S5]

其首次使用仅在用户发送请求后读取近期项目路径、不导入对话文本，说明渐进授权本身可以是重要的产品设计。[S5]

借鉴：持久身份、启动摩擦低、延续用户选择。不要以“长期 Bot”或“手机提醒”本身作为独特卖点。

### OpenClaw

当前 Heartbeat 文档已将监控迁移至普通 Automation：每个任务拥有自己的时间表、上下文、策略和历史，可使用 activeHours 与 idleOnly。[S6]

当前文档明确提醒：旧 Heartbeat 特有的去重与无路由跳过行为已移除，重复更新可能投递；不能把旧版本的通知抑制能力当成现成保证。[S6]

Automation 文档记载 inferred commitments 实验在 v2026.8.1 移除，改用显式 Automation；文档未说明移除原因，不能推断失败归因。[S7]

借鉴：主动检查必须可见、可编辑、可删除；“推断用户想做”与“获得长期跟进授权”分开。版本会变化，应固定验证版本。

## 3. 产品探索：主动性需要三条独立轴

不要把主动性做成一个从低到高的总开关。

- 理解：允许观察哪些项目、哪些会话、哪些内容；是否允许跨项目归纳。
- 打扰：什么事情能立即提醒、哪些进入摘要、哪些仅留在 Inbox。
- 行动：仅建议、自动准备，或在明确范围内委托执行。

用户可能允许持续分析，但不允许任何通知；也可能允许自动测试，但只想每天看一次结果。三者必须独立控制。

“人设”建议表现为持续的协作方式：称呼、语气、工作偏好、关注事项、约定的跟进方式。不能用人设 Prompt 代替执行授权，也不能承诺一个线程永远不压缩、不重启。

## 4. 核心闭环提案

观察 → 候选关注事项 → 用户确认或已存在的明确规则 → 跟进 → 判断是否介入 → 投递 → 用户反馈 → 更新关注状态。

候选事项不自动成为用户承诺。每条主动消息回答：发生了什么；为什么现在值得看；依据是什么；下一步可以做什么。

### 三个首发场景候选

1. 离开电脑后的决策收件箱：被关注的 Codex 任务等待输入，手机收到可操作提醒；过期后卡片失效，不重复请求审批。
2. 返回工作时的恢复简报：说明离开期间的变化、仍未解决的事项、建议首先处理的一件事。证据不完整时明确未知。
3. 有限时间的准备工作：用户明确要求“晚间帮我整理这个项目明天要处理的事”，后台调用 Codex 分析，产出有来源的短清单。

第二阶段再验证跨会话行为建议，例如多次重复返工。必须保留反例和用户纠正，不能根据一次失败断言用户存在稳定习惯。

用户可自然表达“这件事替我盯着”“周五再说”“不用管这个项目”。系统应回显可检查的约定，包括范围、触发条件、有效期和通知方式。

## 5. 推送不是消息出口，而是产品的决策层

建议的介入级别：立即处理、稍后处理、每日摘要、静默记录。级别由用户规则、事项时效和证据共同决定；模型不能自行把所有消息升级为紧急。

最小卡片：事项、变化、证据入口、建议动作、数据更新时间，以及执行/查看/稍后/不再跟进。用户否定时可以选择“已完成”“判断错了”“现在不重要”；不强迫每次填写原因。

建议的投递规则：

- 相同事项的重复事件合并；只有实质变化、用户设定的再次提醒时间或明确升级规则才重新通知。
- 用户正在桌面处理同一事项时，默认不再发手机推送；无法判断在线状态时不可假装已读。
- 生成、投递、送达、阅读、处理分别记账。推送服务接受请求不等于用户收到，更不等于处理完成。
- 稍后处理只改变提醒时间；不再跟进终止后续关注；已读不关闭任务。
- 确认规则撤销后，取消相关排队分析与未发提醒；重启不能悄悄恢复。
- Mac 睡眠时手机显示最后同步时间与主机不可用；不将旧状态显示成实时状态。
- 手机通知的文字按隐私偏好控制。Relay 无法读取端到端加密内容时，不能依靠它生成语义摘要。

预算提案：每天非紧急通知上限、安静时段、项目配额、合并窗口；达到上限后进入 Inbox 或摘要，而不是丢弃事项。具体默认值留待验证，不把“每天两条”当成普适结论。

## 6. 用户管理的两种含义

A. 用户管理 Agent：可见的观察范围、关注清单、预算、授权、提醒规则、历史、暂停与删除。

B. Agent 协助用户管理工作：把目标整理成下一步，追踪明确承诺，发现遗漏与冲突，提醒重新排优先级。

推荐两者都保留，但第一版以 A 保障可控、以 B 的“持续跟进明确关注事项”创造价值。暂不从行为推断用户人格、情绪或生活目标。

尤其要区分：用户说“有空看看支付重构”与“本周五提醒我检查支付重构”。前者可以进入候选，后者可以形成明确提醒。

## 7. 技术边界提案

Mac 常驻服务负责事件接收、持久化、关注规则、工作队列、预算准入与通知投递。Codex App Server 负责语义分析与被委托的执行。Relay 负责连接与加密载荷转发，移动端负责查看和决策。

已有 CLI 的观察和产品托管执行分开标记：先通过经过授权的 Hooks 和历史读取接入；只有完成同会话控制实验后，才宣称能继续或审批用户原来的活跃 CLI。

不要给任意 PID 包装一个“可控制”按钮。每个会话展示真实能力：仅观察、可恢复、可控制、未知/不可达。

状态建议分离：执行状态、工作完成状态、关注状态、通知状态。一次 turn 完成只证明这次执行结束，不能自动证明用户目标完成。

长期记忆建议分为：用户明确偏好、已确认关注事项、有来源的工作事实、可撤销的推断。历史纠正应覆盖后续推理；先前对话中的指令是待分析资料，不得改写当前授权。

初版无需图数据库或通用编排框架。最小持久化对象可包括关注事项、来源事件、分析结果、投递记录、授权与预算记录。最终表结构等待范围确认。

## 8. 主动任务的预算与生命周期

建议事件驱动为主，定时检查作为明确订阅的补充。后台空闲不调用模型；事件先去重，再决定是否值得做语义分析。

开始任务前预留资源额度，完成后结算；中断与错误也记账。达到限额后停止发起新任务，保留已有结果。前台任务优先，后台队列有过期时间，不能在电脑醒来后把积压的旧建议全部推送。

必须区分：订阅用量百分比、token 数、估算 API 费用、可核对的实际费用。Token 事件与中断均可能有延迟，因此预算不能承诺零超额；通过任务上限和保留余量降低超额。

长期 Agent 的后台分析不必强占一个永远运行的会话。稳定身份加可恢复工作状态、按需启动分析，是建议方向；是否复用主对话要通过污染与连续性实验决定。

## 9. MVP 顺序应围绕主动价值调整

原提案先 Observer，再完整 Remote Control，最后才验证 Advisor，会延后最关键的产品假设。

建议：

1. 只支持 Codex，完成可观察性验证，同时做本地跟进与桌面提醒；从第一阶段就验证主动建议。
2. 加入手机 Inbox、通知、稍后处理/取消跟进和主机离线状态；先证明离开电脑后的价值。
3. 按实验结果增加同会话控制与审批；可控与仅观察会话明确区分。
4. 证据足够后才增加预算内自主执行，以及更广泛的行为洞察。

如用户把“手机立即处理原会话审批”列为首发必要场景，步骤 2 与 3 必须一起验收；需要优先做控制通路实验，不能用“手机建议”冒充远控。

## 10. 验证计划与停损条件

### 技术实验

- 多个原生 CLI：是否能关联 session、项目、turn 与进程；重启、崩溃、遗漏 Hook 时是否正确保留未知。
- App Server：订阅、恢复、审批、中断、断线恢复；多客户端下有无重复执行与过期审批。固定安装版本及生成的协议 schema。
- 通知：重复事件、事项已处理、稍后提醒、规则撤销、双端在线、主机睡眠、预算耗尽。验证不再推送过期事项。
- 长期运行：认证失效、服务重启、升级后恢复；避免在失败后无限重试和反复通知。

### 产品实验

先用少量真实授权项目做人工可检查的试用。可先进行一周静默候选采集，再一周允许通知；这只是实验建议，尚无样本结论。

记录每个候选为什么发/不发，避免只评估已发送的“好案例”。用户评价有帮助、无帮助、判断错误、时机错误；独立核对事实与遗漏。

核心观察：提醒是否改变了有效行动；是否减少重复查看会话；错误和过期提醒数量；本该提醒却遗漏的事项；用户主动保留的关注规则；每个有用介入消耗的资源。

不以点击率、通知数或运行时长为成功指标；忽略通知不自动等于拒绝，采纳建议也不自动等于产生价值。

停损：若准确观察现有会话仍做不到，先限制支持的接入方式；若主动建议没有稳定价值，缩小到明确关注事项的可靠跟进，不扩大行为采集。

## 11. 第一轮设计树

已定根节点：常驻个人 Agent；第一版 Codex；主动性和推送是重点。

当前可独立讨论的分支：

1. 首批用户是否就是本人这样的多项目、多 Codex 会话开发者？决定价值验证场景。
2. 第一版是否以用户明确关注的事项为主，自动发现仅生成待确认候选？决定承诺的来源。
3. 第一版是否允许自动只读分析和准备，但代码修改与执行任务由用户主动委托？决定行动权。
4. 第一版观察范围是否限于用户选定的项目与 Codex 活动？决定数据来源。
5. 第一版是否必须包括手机通知和处理 Inbox，而完整远控以技术实验作为准入？决定首发交付边界。

这些答案确定后再讨论依赖分支：角色语气、提醒分类与默认值、计费单位、手机技术栈、长期状态模型、Relay 部署、执行授权粒度。当前不生成虚假的 Accepted ADR。
