## 1. 产品定义

LoopMe 是住在你 Mac 上、会主动跟进事情的个人 Agent。你在手机上和它聊天、接收汇报、替它做决定。

第一版要回答的问题是：一个会主动回来找你的 Agent，是否比一个需要你去找的 Agent 更有用。

第一批用户是内部团队。核心场景是**盯住当前的开发任务**【已确认】。

## 2. 已确认的决策

| 方面 | 结论 |
| --- | --- |
| 平台 | 只做 macOS（Apple Silicon，14 以上）和 iOS（17 以上），其他平台以后再说 |
| 运行位置 | Mac 承载智能、数据和执行；手机是交互入口；Relay 只负责转发 |
| Agent Runtime | 复用 Codex，推荐使用 Codex App Server，由 daemon 以子进程方式启动 |
| 账号 | 不建账号体系，桌面和手机扫码配对，可以解除配对 |
| 信息架构 | 只有**一条对话流**，事项以卡片形式出现在对话中 |
| 默认权限档位 | “自动 · 仅工作区” |
| 桌面离线时的待发送指令 | 第一版不做，只保留未发送的草稿 |
| 网络层 | iroh，在公司内网自建 iroh relay，手机通过公司 VPN 连接 |
| 部署 | 第一版不部署在 Cloudflare；等安全团队确认后再考虑 |
| 推送 | 第一版由 **Mac daemon 直接调用 APNs**，推送密钥随内部版分发（仅限内部使用，风险可控） |
| 分发 | 使用个人 Apple 开发者账号；iOS 走 TestFlight，Mac 使用 Developer ID 签名并公证 |
| daemon 语言 | Rust |
| 会话分析范围 | 每台 Mac 只分析本机的 Codex 会话，结果只给本人；第一版不做团队汇总视图 |

## 3. 核心场景

1. **首次使用**：Mac 检查环境（Codex 是否安装、登录，relay 是否可达）→ 填写 Profile → 选择授权文件夹和权限档位 → 扫码配对，双方核对 4 位校验码 → 发送测试推送 → 设定主动工作计划。
2. **交代跟进**：用户说“帮我盯着 X”，Agent 回复并附上事项卡（检查时间、完成条件、将会做什么）。没有变化时不通知。
3. **早间汇报**：工作日 9:00 汇总进行中的事项，只在有内容可说时才发消息。
4. **从 Codex 会话中找出最重要的事**【已确认方向，细节为建议】：读取本机最近 7 天的 Codex 会话，挑出 3 件最值得跟进的开发任务（例如停在测试失败的会话、几天没动的分支）。用户点“跟进”后才变成事项，点“忽略”则不再推荐。
5. **在手机上做决定**：锁屏通知 → 同意或拒绝 → 显示“已发送” → Mac 确认后才显示“已完成”。Mac 不可达时，按钮置灰。
6. **纠正记忆**：用户可以编辑、锁定或删除记忆。删除的内容进入“不要再记”列表，之后不会被重新写回。

## 4. 页面（详见原型）

- **iPhone**：扫码连接引导页 → 对话首页（顶部显示“需要你”提示条，有事项卡和决定卡，可以停止正在做的工作）→ 设置页（Mac 状态、权限档位、Codex 版本、记忆、Profile、通知时机、安静时段、对话设置、外观、语言、解除配对）。
- **Mac**：菜单栏面板（连接状态、显示二维码和校验码、Codex 版本与就绪状态、内网 relay、下次唤醒时间、插电时保持唤醒）。

## 5. 最小领域模型【建议】

Profile、MemoryEntry（状态为 active / locked / deleted，删除时保留墓碑记录）、Message（单调递增序号）、Item（事项）、Decision、Wake、Run、CodexSession（内部使用，对用户不可见）、Notification（outbox）、Device。

事项状态：已安排 → 进行中 → 需要你 → 已完成 / 不再跟进；另有“稍后提醒”。

## 6. 行为规则

- 只有桌面确认过的状态才算数。手机上的操作在收到确认前一律显示“已发送”。
- 每个写操作都带客户端生成的 ID，由 daemon 去重；重连时按序号补发增量。
- 只有三类情况会通知：需要你决定、交代的事有结果、执行失败需要你介入。
- 默认数值【已确认，可配置，内部期当作实验参数】：同一事项每天最多提醒 2 次；全局每小时最多 5 条；决定 48 小时未答视为拒绝；连续 10 次检查无变化后，询问是否继续跟进。

## 7. 技术选型

| 部分 | 选择 |
| --- | --- |
| 共享核心 | Rust `loopme-core`（协议、加密、同步、iroh）；daemon 直接使用，iOS 通过 UniFFI 调用 |
| Mac 界面 | SwiftUI `MenuBarExtra` + `LSUIElement` |
| Mac daemon | Rust，通过 `SMAppService.agent` 注册为 LaunchAgent；与界面壳之间通过 Unix domain socket 通信，协议为 JSON-RPC |
| 存储 | 桌面用 SQLite（rusqlite）；iOS 用 SQLite（GRDB）做缓存 |
| 密钥 | Keychain |
| iOS 推送 | APNs；通知支持“同意 / 拒绝”动作；后续用 Notification Service Extension 在手机上解密摘要 |
| 更新 | Sparkle 2，更新源放在内网 |

## 8. 待验证（P0 技术探针）

1. Codex App Server 能否被 daemon 长期托管，审批请求能否挂起数小时等待手机回答。
2. 能否通过 App Server 接口列出历史会话；如果不能，再考虑读取 `~/.codex` 下的会话文件（格式可能随版本变化）。
3. iroh 能否关闭 n0 的公共地址发现，只使用内网 relay；iOS 上的 Swift 绑定能否正常工作。
4. Mac 直接调用 APNs，到 iPhone 被唤起并加载正文的完整链路。

## 9. 实施阶段【建议】

1. **P0 技术探针**（约 1 周）：完成第 8 节的验证。
2. **P1 桌面单机 Agent**：菜单栏面板 + daemon + 对话、记忆、事项、定时唤醒、权限与停止。
3. **P2 手机入口**：配对、iOS 三个页面、推送、同步与去重、离线缓存、加密通知摘要。
4. **P3 打磨**：通知快捷操作、调整频率参数、事项自动收尾、丢机流程。

## 10. v0 实现说明（2026-11-05）

第一版源码已按本文实现，以下几处为了能尽快在本地构建联调，先做了简化，细节见 [architecture.md](architecture.md)：

- 网络层先用“手机经 VPN/局域网直连 Mac 的 WebSocket + 应用层端到端加密”（X25519 + HKDF + ChaCha20-Poly1305，4 位校验码配对），iroh 和内网 relay 后续替换传输层即可。
- daemon 先由菜单栏 App 以子进程方式启动，LaunchAgent 后续再做。
- iOS 端用 CryptoKit 实现同一套加密，暂不通过 UniFFI 复用 Rust 核心。
